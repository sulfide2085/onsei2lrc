# onsei2lrc —— 日语音频 → 中日双语 LRC

给**自用**场景做的本地流水线：`wav/mp3` → 日语转写 → LLM 翻译 → `.lrc`。
针对语音作品（ASMR / 音声 / drama CD / galgame 语音）优化，**全流程离线，素材不出本机**。

```
wav/mp3 ──> 混合切块(VAD+能量) ──> anime-whisper 逐块转写 ──> 断句清洗 ──┐
                                                                        │  ← 阶段①：ASR 全部跑完
                                                        卸载 ASR 模型 ──┘     然后才放掉 whisper
                                                                        │
       加载 Sakura ──> 逐轨翻译（4 并发）──> 文件名翻译 ──> .lrc ────────┘
            └─ 阶段②：译完正文与文件名，再卸载 Sakura
```

## 0.01 两阶段显存编排（为什么要分两段跑）

**问题**：Sakura-7B 常驻要吃 **6.25 GB**，而这张卡只有 **8 GB**。ASR 和 Sakura 同时在场时显存贴顶，
WDDM 开始换页、GPU 发热降频，**ASR 直接掉速**。本机实测同一批音频：

| 显存里同时有什么 | ASR 速度 |
|---|---|
| 只有 whisper | **20.0x 实时** |
| whisper + Sakura（贴顶） | **3.7x 实时**（慢 5.4 倍） |

**做法**：不再「一个文件走完全流程」，而是**按阶段切**：

```
阶段① ASR   所有音轨依次转写 → 落 .segments.json 缓存 → 卸载 ASR 模型（显存 1.6 GB → 0.7 GB）
阶段② 翻译  加载 Sakura（显存 → 6.7 GB）→ 逐轨翻译 → 顺便译文件名 → 卸载 Sakura（显存 → 0.6 GB）
```

显存峰值从「两个模型叠加」变成「取两者较大的那个」，ASR 那段显存基本是空的，不再降频。
每个音轨的 ASR 用时/倍速、翻译用时/行速都会逐轨打印。

**收尾报告**（每次跑完都会打印）：

```
==========================================================================
完成报告
==========================================================================
ASR 阶段 ：6 轨 / 178.9 分钟音频 / 用时 13分32秒 / 平均 13.2x 实时
  音轨                                          音频         用时        速度
  01_和W吸血鬼文化交流的神明体验♡…                30.5分     91.5s    20.0x
  ...
翻译阶段 ：6 轨 / 1412 行 / 用时 6分06秒 / 平均 3.9 行每秒
  音轨                                          行数        用时        速度
  ...
文件名   ：33 个 / 用时 12秒
总计     ：20分05秒
显存驻留 ：ASR 阶段 1.6 GB → 翻译阶段 6.7 GB（分时复用，不再叠加成 8.3 GB）
==========================================================================
```

**命中缓存的那一段不会报假速度**：断点继续时显示「用时 0.0s（命中缓存，未重新转写）」，
平均速度只统计真正干活的轨。

**文件名翻译挪进了阶段②**：以前是下载时才翻（要为了几个文件名把 6 GB 模型重新加载一次），
现在趁 Sakura 在场顺手做掉，译名落到 `<outdir>/_filenames.json`，WebUI 打包时直接读。

> 只有 LM Studio 由本工具加载/卸载（`--manage-backend`，WebUI 会自动带上）。
> llama.cpp / Ollama / DeepSeek 是常驻服务，不该越权去动它们——命令行单独用时默认不开这个开关。
> **两阶段本身恒定开启**，因为它对显存只有好处，产出与旧版完全一致。
>
> CLI 对照：`--phases asr|translate` 只跑其中一段；`--translate-names` 顺带译文件名。

## 0. 完整流程（这条链路是怎么走的）

```
① 输入      音频文件 / zip 压缩包
             zip 自动解包，兼容日文作品的「非 UTF-8 标志 + CP932 文件名」（否则会变乱码）

② 解码      ffmpeg/PyAV → 16kHz 单声道 float32 PCM
             格式无关：wav / mp3 / m4a / flac 一视同仁，容器格式不影响推理速度

③ 切块      hybrid 混合切块（默认）
             ├─ Silero VAD 按静音切出「语音块」→ 时间轴准
             └─ 空隙（>6s）用能量切块补齐 → 舔耳/水音等非语言内容不漏
             VAD 阈值自动下探 0.4→0.25→0.15（耳语作品不漏台词）

④ 转写      anime-whisper（CTranslate2 int8）逐块转写，语言固定日语
             · 绝不设 initial_prompt（官方警告会致幻觉）
             · no_repeat_ngram_size=5 + condition_on_previous_text=False 抑制复读幻觉
             · 不信模型自己的时间戳（该转换版时间戳是坏的），时间轴一律取切块边界

⑤ 清洗      幻觉黑名单（「ご視聴ありがとうございました」等）→ 连续重复去重
             → 间隔过小的短段合并 → 超长句按「。、！？」切分（LRC 可读性）

⑥ 翻译      Sakura 官方 prompt，多行批量（默认 8 行/批，上下文更连贯）
             行数不匹配时：先拆半重试 → 再逐行兜底；结果写入 *.segments.json 缓存

⑦ 输出      LRC（zh 纯中文 / both 中日双语 / ja 纯日文 / inline 一行内）
             时间戳格式 [mm:ss.xx]

⑧ 打包      按需：WAV→MP3 320kbps（保持采样率与声道，绝不 downmix）
             LRC 与音频同名 → 播放器可自动加载
```

## 0.1 WebUI（推荐日常使用）

```bat
cd onsei2lrc
python webui.py                 :: 默认 http://127.0.0.1:7860
python webui.py --port 8000     :: 换端口
```

浏览器打开 **http://127.0.0.1:7860**，页面分四步：

| 区域 | 能做什么 |
|---|---|
| ① 导入 | **两种来源**：拖拽上传音频 / **zip 压缩包**（可多选）；或**直接选本机文件夹**（推荐，见下） |
| ② 设置 | **LRC 样式**（唯一常显项）；折叠的**高级设置**里放翻译后端 / 模型预设 / 提示词模板 / 切块模式 / 单行字数 / 合并间隔 / 批大小 / 并发数 / 采样参数。**没有开关** |
| ③ **任务队列** | 一个文件夹 = 一个任务；可连续加入多个，**串行执行**；每行显示状态/进度，完成的直接带下载按钮，排队中的可「移除」 |
| ④ 日志 | 实时滚动流水线输出 + **两条进度条**（当前文件 / 总任务，按音频时长加权） |
| ⑤ 下载 | **3 个复选项**（默认只勾「WAV 自动转 MP3 320K」）+ **2 个下载项**（下载字幕 LRC / 下载含音频压缩包）+ **「字幕写回音频文件夹」按钮** |

**转写与翻译恒定执行**，界面上不再给开关——它们本来就是主流程。
**转码、打包、文件名翻译都改到「下载」时按勾选触发**：只下字幕就不浪费时间，也不白占磁盘。

### 任务队列

一个文件夹 = 一个任务。点「加入队列」后输入框会清空，方便连续把多个作品丢进去；
队列**串行执行**（GPU 只有一个，并发只会互相拖慢，早先没队列时同时起两个任务会互相抢显存）。

- **刷新浏览器不影响**：队列状态在服务端，页面加载后自动接上
- **排队中的可移除**：`/api/queue/remove`；「取消当前」只作用于正在跑的那个
- **开跑前检查翻译后端**：后端掉线或模型被卸载时，任务**留在队首**并每 20 秒重试，
  界面显示「⏸ 等待翻译后端…」。这一条是踩坑加的——实测 LM Studio 的模型会被
  空闲卸载，没有这个检查的话队列里每个任务都会跑完 ASR 才在翻译那步失败，几小时白跑

| 接口 | 作用 |
|---|---|
| `GET /api/queue` | 队列快照：`pending` / `current`（含 `waiting`、`resume` 标志）/ `finished` |
| `POST /api/queue/remove` | 把排队中的任务移出队列 |
| `POST /api/queue/retry` | 把失败/中断的任务重新入队，**带断点继续** |
| `POST /api/queue/clear` | 清空所有待跑任务 |
| `POST /api/cancel` | 排队中的移出队列；正在跑的终止其子进程 |

### 断点继续

长任务最怕跑到一半断掉。这里有两层保障：

**① 任务状态落盘** —— 每个任务把自身状态写到 `webui_runs/<run_id>/task.json`
（源目录、参数、状态、产出清单）。服务重启时 `_restore_tasks()` 自动：

- **已完成/失败的** → 恢复出来，`_rebuild_pairs()` 从磁盘重建下载清单，**产出仍可下载**
- **跑了一半被中断的** → 重新入队，并带上断点继续标志

**② 检查点就是 `.segments.json`** —— 流水线本来就按文件缓存转写+译文，
继续时加 `--retranslate --reuse-translation`，已完成的部分只做「载入缓存 + 重写 LRC」：

```
[缓存] 复用 第1章.segments.json 的 5 段转写结果
[翻译] 缓存里已有全部译文，跳过翻译
```

**实测**（3 个 30 秒音轨，全部已缓存）：

| 场景 | 耗时 |
|---|---|
| 全新跑 | 33.3s |
| **断点继续（全部已完成）** | **0.2s**（省 99%） |
| 只复用转写（`--retranslate`） | 6.7s |
| 默认（什么都不加，重跑） | 32.9s |

中断场景实测（4 个音轨，跑到第 3 个时强杀服务）：重启后自动继续，跳过已完成的 2 个，
**29.0s vs 全新 39.4s**。省下的比例 = 跳过的文件比例，只扣掉固定的 ASR 模型加载（约 8 秒）。

> 踩坑记录：`resume` 是任务级状态（存在 `st` 上），而 `build_cmd` 从 `st["options"]` 读参数——
> 一开始忘了同步，导致标志没传到命令行，断点继续静默失效。现在 `run_pipeline` 开头会同步。
>
> 另一个坑：`_restore_tasks()` 里用了 `log.info()` 但模块没有 logger，
> **有任务可恢复时服务会直接起不来**。现在恢复逻辑整体包了 try/except，
> 且用 `--no-restore` 可跳过恢复。

### 下载区的勾选怎么影响压缩包

| 勾选项 | 默认 | 作用 |
|---|---|---|
| **附带日文 lrc** | ☐ | 把 `<名字>.ja.lrc` 一起放进包里。**也决定「字幕写回」写几个文件** |
| **WAV 自动转 MP3（320K）** | ☑ | 「含音频」包里把 WAV 等转成 MP3 320k；**已是 MP3 的原样引用，不重新编码**。本次没有非 MP3 音频时该框自动禁用 |
| **翻译文件名** | ☐ | 用同一个翻译模型把音频文件名译成中文，**音频、`.lrc`、`.ja.lrc` 一起改名**，保持同名配对 |

> 默认只勾「WAV 自动转 MP3」：音声素材常见几 GB 的 WAV，转成 MP3 才好用；
> 日文 lrc 和文件名翻译属于按需才要的，默认关掉可少一次翻译调用、也少些文件。

**文件名翻译的几个实现要点**（都是踩过坑才加的）：

- **采样温度必须压低**：`temperature=0.2`。文件名翻译是「翻译」不是「创作」，
  用服务端默认温度（通常 0.8）实测**同一批跑两遍有 85% 的条目不一样**，
  压低后降到 33%（33 个文件名里 21 个两遍一致）。
- **结构信息用确定性规则兜底**，不交给模型：编号前缀（`第1章` 被模型改写成 `序章` 会毁掉排序）、
  右括号补齐（模型会把 `『お寺内』` 译成 `『寺院内部` 丢掉右括号）、全角转半角（`４`→`4`）、
  Windows 非法字符、重名加序号。
- **`.ja.lrc` 要一起改名**：`Path("X.ja.lrc").stem` 是 `X.ja` 不是 `X`，直接查表会漏掉，
  导致中文 LRC 改了名、日文 LRC 没改，**两者配不上对**。

| 下载项 | 内容 |
|---|---|
| **下载字幕 LRC** | `<名字>.lrc`（+ `.ja.lrc` 若勾选；文件名可翻译） |
| **下载含音频压缩包** | 上面 + 音频（原始文件；勾了转 MP3 则换成 MP3） |

`.segments.json` 是**本工具的翻译缓存，不进任何下载包**，只留在 `webui_runs/<run_id>/output/`。
含音频的包可能几 GB，所以不在运行时预先打，而是**首次点击时才生成**并缓存。

### 字幕写回音频文件夹（按钮）

文件夹模式下，跑完**不会自动**把字幕放进音频目录——改成按钮，因为写回会改动你的素材目录，
应该由你明确按一下。

- 按钮在 ⑤ 下载区，**只有「文件夹模式 + 本次已有字幕」时才可点**
- 按钮上方会写明「将 N 个 .lrc 复制到 &lt;目录&gt;」，N 跟着「附带日文 lrc」变
- 点击后弹确认框，写明**只会新增 `.lrc`，同名文件会被覆盖，不会改动或删除任何原有文件**
- 只写 `.lrc`；`.segments.json` 是本工具的缓存，不写进音频目录
- 可以重复点（幂等）

顶部有健康检查徽章：ffmpeg、ASR 模型、LM Studio / llama.cpp / Ollama 是否在线。

### 两种导入方式

**上传**：拖拽文件或 zip。文件会经浏览器复制到 `webui_runs/<run_id>/input/`，适合远程或零散文件。

**本机文件夹**（推荐）：点「选择本机文件夹」→「浏览…」打开目录浏览器（列出盘符 → 逐层进入，
每个文件夹标注音频数量，🎵 表示本层有音频）→「使用此文件夹」。
**服务端直接读盘，不经过浏览器上传**，几百 MB 到几 GB 的音声文件夹秒开。

文件夹模式的行为：

| | 说明 |
|---|---|
| 递归处理 | 子目录会一起处理，并**保持目录结构** |
| 写回源目录 | **跑完不自动写**；要写回请点 ⑤ 下载区的「字幕写回音频文件夹」按钮。写的是 `.lrc` / `.ja.lrc`（后者取决于「附带日文 lrc」勾选），**同名，播放器可自动加载**；**只写 `.lrc`，不写 `.segments.json`**（那是本工具的缓存，不属于产物）；**只新增文件，绝不改动或删除原文件** |
| 不解包 | 源目录里的 zip **不会**自动解包（避免往你的目录里写中间文件）；需要解包请用上传模式 |
| 不动音频 | 运行时**完全不碰音频文件**——不转码、不复制。要音频就去「下载」里点对应选项 |

实测（3 个音频 / 含中文路径 / 含子目录）：

```
[输入] 本机文件夹：D:\...\RJ99999999 测试音声
[输入] 共 3 个音频文件  音频总时长 0.9 分钟
[输出] ...\output\1.正篇\01 开场.lrc（5 行）
[写回] 已把 9 个字幕文件写入 D:\...\RJ99999999 测试音声
```

源目录结果：每个音频旁边多了同名的 `.lrc`（中文）和 `.ja.lrc`（日文原文）。
`.segments.json` 翻译缓存留在 `webui_runs/<run_id>/output/` 里，不会污染你的音频目录。

常见用法：
- **默认跑一遍** → 得到字幕；需要音频时再去「下载」勾选后下载
- **要 MP3**：勾「WAV 自动转 MP3（320K）」再点「下载含音频压缩包」，首次点击时转码
- **要原始音频**：不勾转码，直接点「下载含音频压缩包」，原始文件原样打包
- **要中文文件名**：勾「翻译文件名」，音频与字幕一起改名，保持配对
- **用 DeepSeek**：后端选 DeepSeek，填 API Key（注意云端服务有内容审核策略）

### 音频处理规则（MP3 会不会被二次转码？——不会）

| 源文件 | 勾「WAV 自动转 MP3」 | 不勾 |
|---|---|---|
| `.wav` 等非 MP3 | **点击时**转成 MP3 320k | 原样打包（WAV 还是 WAV） |
| `.mp3` | **原样引用，不重新编码** | 原样打包 |
| `X.wav` 且同目录已有 `X.mp3` | **跳过 X.wav**，用现成的 X.mp3 | 原样打包 X.wav |

**位级实测**（MD5 比对，压缩包内文件 vs 源文件）：

```
源文件                       输出                        结论
乙.mp3 (320k, 322,653 B)  →  乙.mp3 (322,653 B)  55bb426cbdaa  ✅ 逐字节相同
丙_低码率.mp3 (128k)       →  丙_低码率.mp3        214e3835bf11  ✅ 逐字节相同（未被升成 320k）
甲.wav (24bit PCM)        →  甲.mp3 (322,651 B)  80e0c648c41b  （新生成的转码产物）
```

所以：**MP3 永远不会被二次转码**，码率也不会被改动——即使勾了「WAV 自动转 MP3」，
128k 的 MP3 出来还是 128k。只有非 MP3 格式才会走 ffmpeg 转码。

**同名冲突保护**：如果同一目录里同时有 `X.wav` 和 `X.mp3`，两者都会输出 `X.mp3`，
WAV 的转码产物会把现成的 MP3 覆盖掉。现在检测到这种情况会**跳过 WAV**，直接用现成的 MP3：

```
[跳过转码] 丁.wav：同目录已有同名 MP3，下载 MP3 包时直接用
```

**打包体积**：下载区显示的音频体积是**源文件的原始大小**（标了「约」）。
zip 会压缩，PCM 类 WAV 尤其明显——实测 6.26 MB 的 24bit WAV 压出来只有 2.88 MB。

WebUI 只监听 `127.0.0.1`，不上传任何数据到外部；文件夹模式更是完全不经过网络传文件。

## 0.15 术语表 与 ASR 修正表（两个不同环节，别搞混）

| | 作用环节 | 格式 | 解决什么 | 是否通用 |
|---|---|---|---|---|
| **术语表** `--glossary` | **翻译时** | `日文->中文 #备注` | 同一术语译法不统一（前后用词不一致） | ✅ 跨作品通用 |
| **ASR 修正表** `--fix-asr` | **转写后、翻译前** | `听错的=>正确的 #备注` | **ASR 听错的字**——错字已在日文原文里，翻译环节救不了 | ❌ 每个作品不同 |

WebUI 里两块文本框都能直接粘贴，也能「从文件载入」，内容存在浏览器本地（下次打开还在）。

### 术语表：只放通用条目，别过拟合

术语表是**纯文本、自己维护**的，格式一行一条：

```
日文->中文 #可选备注
```

`glossary_template.txt` 是空模板，只写了格式说明。**本仓库不附带成品术语表**——
具体收哪些词取决于你的素材和偏好，请自行维护，并把它加进 `.gitignore`。

**收录标准：跨作品通用。** 题材、称呼类的通用词可以进；
**具体角色名不要固化**（`角色名->译名` 这种），每个作品都不同，固化进来只会在下一个作品里帮倒忙，
而且模型通常能自行音译、同一作品内本来就一致。真需要时**临时追加**几条、用完删掉即可。

术语表会**随每次请求一起发送**，所以条目别太多（几十条以内），否则拖慢速度、还可能挤占上下文。

### ASR 修正表：没有通用条目，只能逐作品校对

ASR 错字是**随机**的，不存在跨作品通用的修正条目，所以 `asr_fixes_template.txt` 默认是空的，
只写了格式说明。标准流程：

```bat
:: ① 先跑一遍，拿到日文原文（--keep-ja 会输出 .ja.lrc）
python onsei2lrc.py "音频目录" --preset lmstudio --model-name sakura37 --prompt-style v3 --keep-ja --outdir out

:: ② 对着音频校对 out\*.ja.lrc，把听错的记进修正表
::    格式：听错的=>正确的   （# 开头是注释，行尾可加 " # 备注"）

:: ③ 带修正表重跑 —— 只有被改动的行会重译，几秒钟完成
python onsei2lrc.py "音频目录" --retranslate --reuse-translation ^
    --fix-asr asr_fixes.txt --glossary glossary_common.txt ^
    --preset lmstudio --model-name sakura37 --prompt-style v3 --outdir out
```

实测：改 2 处错字 → **2.8 秒**完成（全量重译需 414 秒）。原始转写会留档在缓存的 `ja_raw` 字段，随时可回查。
一个 87 分钟的作品通常只有几条错字，校对成本很低。

**配置指纹**：缓存里会记录「术语表哈希 + 提示词模板 + 模型 + 采样参数」。只要其中任何一项变了，
`--reuse-translation` 会自动失效并全部重译，不会出现「改了术语表却没生效」的静默错误。

## 2. 三种切块模式（时间轴的关键）

**背景**：那个 CT2 量化版的时间戳是坏的 —— 13 秒语音被标成 `[0.00-0.42]`；90 秒音频只在 30 秒窗口
边界给 `[0.00-0.42] [30.00-30.78] [60.00-60.08]`（同段音频用 `tiny` 测正常，所以是转换版的问题）。
本工具的做法是**不信模型的时间戳，改由切块边界提供时间**，有三种模式：

| 模式 | 做法 | 适用 |
|---|---|---|
| `vad` | Silero VAD 按静音切块，逐块转写 | 台词为主的作品，时间最准 |
| `energy` | 按能量切块，覆盖 100% 音频 | 几乎全是非语言音的作品 |
| **`hybrid`（默认）** | 台词段用 VAD 边界，**空隙（>6s）用能量块补齐** | 最稳，兼顾准与全 |

为什么需要 hybrid：某轨（舔耳）有 **2 分钟内容被 VAD 整段跳过**——那段能量其实比台词段还高
（-25.4 vs -27.7 dBFS），是连续舔耳/水音，Silero 判为非语音；而 anime-whisper 恰恰能转写这些声音，
参考译文也确实把「挠啊挠啊挠啊……」「啾噜噜噜噜！」这类内容写进了 LRC。

**VAD 阈值自动下探**：默认按 `0.4 → 0.25 → 0.15` 逐级尝试，直到语音覆盖率达 `--vad-min-coverage`（默认 25%）。
耳语/舔耳类作品能量极低，固定 0.4 会大量漏台词（实测该轨覆盖率仅 17%、命中率 40%）。

**实测（tr05 舔耳轨，与参考译文比对）**

| 模式 | 参考行命中率(±3s) | 平均绝对时间误差 |
|---|---|---|
| `vad` | 54.9% | 0.72s |
| `energy` | 78.8% | 1.36s |
| **`hybrid`** | **87.6%** | **0.95s** |

## 4. 本机踩到的三个坑（已内置修复）

**坑 1：`cublas64_12.dll is not found`**
`ctranslate2 4.5` 要 CUDA 12 运行时，而本机 torch 是 cu118（只有 `cublas64_11.dll`）。
`ensure_cuda_dlls()` 会自动在 conda 各环境的 `site-packages\torch\lib`、`site-packages\nvidia\*\bin`、
Ollama 的 `cuda_v12`、LM Studio backend 目录里找并注册。本机命中
`<你的 conda 环境>\Lib\site-packages\torch\lib`（需含 cublas 与完整 cuDNN 9）。
找不到时用 `--cuda-dll-dir` 手动指定。

**坑 2：本地模型请求 502 Bad Gateway**
`curl` 调 `127.0.0.1:1234` 正常，Python `openai` 库一律 502。原因：本机开着系统代理
（注册表 `ProxyEnable=1, ProxyServer=127.0.0.1:7890`），而 `httpx` 默认 `trust_env=True`
**会读 Windows 注册表的代理设置**，把本地请求也丢给代理。
修复：`_make_client()` 检测到 `base_url` 是本地地址就用 `httpx.Client(trust_env=False)` 直连。

**坑 3：`word_timestamps=True` 直接崩进程**
那个 CT2 int8 模型开词级时间戳会访问冲突（`0xC0000005`，CPU/GPU 都一样）。
所以 `--hallucination-silence` 默认 **0（关闭）**（它依赖 word_timestamps）。别硬开。

**坑 4：`Path.with_suffix()` 会吃掉文件名里的点**
像 `1.イントロ.wav` 这种文件名，`Path('1.イントロ').suffix` 是 `'.イントロ'` 而不是 `''`，
于是 `with_suffix('.lrc')` 会把描述部分替换掉，输出成 `1.lrc`（描述丢了，还可能与别的音轨重名）。
已全部改成字符串拼接：`base / (audio.stem + ".lrc")`。

## 4.1 格式对速度的影响（实测）

流水线第一步就把任何格式解码成 16kHz 单声道 float32 PCM，模型只吃 PCM，所以**容器格式不影响推理速度**。
同一段 9.7 分钟音频（WAV 24bit/48k vs 转出的 MP3 320k/48k）：

| 指标 | WAV | MP3 320k |
|---|---|---|
| 文件大小 | 160.3 MB | 22.3 MB |
| 解码耗时 | 0.47s（1242x 实时） | 0.91s（640x 实时） |
| 端到端 ASR 总耗时 | 50.7s | 51.8s（**+2.0%**） |

WAV 反而略快（读 PCM + 重采样 vs 熵解码）。**真正有差别的是转写内容**：时间轴 95.3% 的行在 ±3s 内
一致（中位差 0.000s），但文字只有 43.4% 逐字相同——大部分是拟声词在相邻行之间挪位置，
也有真听错的（一个词的送假名被听成另一个词，意思完全变了）。原因是这类作品大量内容是
高频低电平的非语言音（耳语/水音/吐息），正是 MP3 心理声学模型丢弃信息最多的地方。

**结论**：跑 ASR 用原始 WAV（或 FLAC）最好；只是听的话 MP3 320k 完全够，且转码后时长偏差
≤42ms，**已有 LRC 可直接沿用**，不必重跑。

## 6. 与自带译文的逐轨比对（7 轨 / 87 分钟 / 参考 501 行）

以某部自带官方译文的作品为参照（参考译文每一行都当作「该时刻应有内容」，
看本工具输出能否在 ±3 秒内命中）：

| 音轨 | 本工具行数 | 参考行数 | 时间轴命中率(±3s) | 平均绝对时间误差 |
|---|---|---|---|---|
| tr00 | 5 | 4 | **100%** | 0.45s |
| tr01 | 59 | 41 | 87.8% | 0.32s |
| tr02 | 203 | 104 | 87.5% | 0.56s |
| tr03 | 138 | 57 | 94.7% | 0.65s |
| tr04 | 124 | 82 | 81.7% | 0.56s |
| tr05 | 164 | 113 | 87.6% | 0.95s |
| tr06 | 156 | 100 | 93.0% | 0.94s |
| **合计/平均** | 849 | 501 | **90.3%** | **0.63s** |

本工具行数普遍更多，是因为按停顿断行（参考译文倾向合并成整句）。

**译文质量**（tr01 抽样，Sakura vs 官方译文）：

- 大量句子与参考**逐字一致**
- 语义一致、措辞不同：「你真的每天在这种地方生活吗？」/「你真的每天生活在这种地方吗」
- 更口语或更直译的差异：「傻乎乎的脸孔。」vs「呵呵……瞧你那蠢脸」

**已知问题（如实说明）**

1. **ASR 错字会传导到译文**：把「主食」听成「試食」→ 译文跟着错；「抵抗する気力」听成「抵抗する記録」。
   这是 ASR 环节的锅，换更大模型或加 `--glossary` 可缓解。
2. 偶发短碎片行（「呐……」单独一行）——`--merge-gap` 调大即可。
3. 极少数句子偏直译、缺标点——`--batch-size 12` 让上下文更足会好些。
4. 参考译文里有些行是**对声音的描述**（如喘息的拟声），
   本工具靠 anime-whisper 直接转写非语言发声，风格上更"原声"、信息量略少。

## 10. wav2mp3 —— 可复用的转码工具（库 + 命令行）

`wav2mp3.py` 是**单文件、无第三方依赖**的模块（只要 ffmpeg / ffprobe），
复制到自己项目里就能 `import`。

### 作为库

```python
from wav2mp3 import to_mp3, to_mp3_batch, probe, find_audio, summarize

# 单文件
r = to_mp3("input.wav", "output.mp3")          # dst 可省略，默认同目录同名
if r.ok:
    print(f"{r.dst_bytes} 字节，压缩到 1/{r.ratio:.1f}")
else:
    print("失败:", r.error)

# 批量：输入可以是文件、目录或混合；返回结果严格按输入顺序
results = to_mp3_batch(
    ["D:/音声/RJ00000000", "D:/另一个.flac"],
    outdir="D:/输出",              # 省略则写在源文件旁边；给了就保持相对结构
    quality="vbr0",                # cbr320(默认) / vbr0 / vbr2 / cbr192
    jobs=8,                        # 默认 min(4, CPU核数)
    on_progress=lambda i, n, r: print(f"[{i}/{n}] {r.src.name}"),
)
s = summarize(results)             # 统计字典：done/skipped/failed/ratio/errors…

# 只看信息、只收集文件
info = probe("input.wav")          # AudioInfo(sample_rate, channels, duration…)
files = find_audio(["D:/音声"], recursive=True, exts=("wav", "flac"))
```

**API 一览**

| 符号 | 说明 |
|---|---|
| `to_mp3(src, dst=None, *, quality, overwrite, tags, title, timeout)` | 转单个文件，返回 `ConvertResult` |
| `to_mp3_batch(inputs, *, outdir, quality, jobs, overwrite, tags, recursive, exts, dry_run, on_progress)` | 批量，返回按输入顺序的结果列表 |
| `probe(path)` | 读音频信息，失败返回 `None` |
| `find_audio(paths, *, recursive, exts)` | 摊平成文件列表（去重、排序） |
| `summarize(results)` | 汇总统计字典 |
| `check_ffmpeg()` / `set_ffmpeg_path()` | 检查 / 指定 ffmpeg 位置 |
| `AudioInfo` / `ConvertResult` / `AudioError` / `FFmpegNotFound` | 数据结构与异常 |
| `QUALITY_PRESETS` / `AUDIO_EXTS` / `MP3_SAMPLE_RATES` / `human` | 常量与工具函数 |

**设计约定**

- **不抛异常**：单文件失败信息放在 `result.error` 里，`ok=False`。
  想用异常就调 `result.raise_for_error()`。批量同理，一条失败不影响其他条。
- **无副作用**：`import` 不打印、不读写文件、不检查 ffmpeg（0.04 秒）。
- **顺序保证**：`to_mp3_batch` 的返回值与 `find_audio` 的输出一一对应，
  与完成先后无关。`on_progress` 回调则按完成顺序触发。
- **日志走 `logging`**，模块 logger 名为 `wav2mp3`。

### 作为命令行

```bat
python wav2mp3.py "D:\音声\RJ00000000"
python wav2mp3.py a.wav b.flac -o D:\out -q vbr0 -j 8
python wav2mp3.py "D:\音声" -n                  :: dry-run
python wav2mp3.py "D:\音声" --delete-source     :: 转完删源（危险，先 -n 看看）
```

### 行为约定

- **保持采样率与声道，绝不 downmix** —— 音声/ASMR 多为バイノーラル或ダミヘ录音，
  立体声里编码的是空间方位信息，压成单声道会把整个 3D 声场拍平。
- **默认跳过 MP3** —— `AUDIO_EXTS` 故意不含 mp3，重新编码只会劣化。
  要处理 MP3 请显式传 `exts=("wav", "mp3")`。
- **不覆盖已有产物**（除非 `overwrite=True`），批量中断后重跑不会重做已完成部分。
- **采样率处理**：在 MP3 支持表内（8/11.025/12/16/22.05/24/32/44.1/48 kHz）原样保留；
  超出（如 96k）才重采样到最接近的有效值，并在 `result.notes` 里写 `resampled:96000->48000`。
- **低采样率码率封顶**：≤24 kHz 属 MPEG-2 档位，码率上限 160k，LAME 静默封顶，
  `result.notes` 里写 `capped:320->160`。
- **ID3v2.3** —— 默认的 v2.4 在 Windows 资源管理器、老播放器、车机上对中日文标签
  支持很差会显示乱码；v2.3 兼容性最好。`tags=True` 时用 `-map_metadata 0` 继承源标签。

**存特征而不是只存路径** —— 音频一旦移动或改名，只存路径的标注就废了。

### 性能：目录浏览为什么要这么写

最初版本给每个子目录做**递归** `rglob` 数音频，还给了每个目录 0.35 秒预算。
实测 `D:\` 列一次目录要 **12.9 秒**，完全不可用。

改成**只数直接子文件**（一次 `iterdir`）后：

| 目录 | 递归计数 | 直接计数 |
|---|---|---|
| `C:\` | 3495 ms | **45 ms** |
| `D:\` | 12873 ms | **151 ms** |
| `D:\库\音声\含高潮时间` | — | **4 ms** |

`iterdir` 在任何目录上都是 0~2 ms。子目录里没有直接音频时显示 `›` 表示「还有下级」。

**为什么不显示递归总数**：那种数字要么慢、要么不准。用一次瞬时 `iterdir` 换来的
「这一层有几个音频」已经够判断该不该点进去。

**为什么单独做一个**：`webui.py` 是转写+翻译的批处理界面；
这个播放器只做「听的时候知道哪儿是高潮」这一件事，所以按路径直读、不产生任何输出文件。

## 11. climax_finder —— 高潮（射精）候选点检测

从日语音频里找出可能的高潮时刻。**候选生成器，不是自动打标机。**

```bat
python climax_finder.py "D:\音声\RJ00000000\01_mp3"                    :: 默认 ml 模型
python climax_finder.py "目录" --transcript-dir "转写目录" --top 5
```

### 11.1 实测指标（10 折留一作品交叉验证）

**69 轨 / 92 个官方标注点 / 20.8 小时音频 / 10 部作品**（其中 **13 轨标着「0 次」**，
也必须计入 —— 模型会在那里输出候选，全是误报）。
每折：9 部训练，1 部完全未见。

**两种聚合口径都列出来，因为它们的含义不同**：

| 口径 | 精确率 | 召回率 | 回答的问题 |
|---|---|---|---|
| **逐折平均**（	rain_model.py 打印的） | **48.9%** | **72.9%** | 「处理一部作品时，表现如何」 |
| 全部汇总（总命中/总候选） | 48.1% | 68.5% | 「所有高潮点里，找到了多少」 |

各折候选数不等（12~30 个），所以逐折平均会给小作品更高权重。
**用户是一次处理一部作品的，所以逐折平均更贴近实际体验**；汇总值更保守。

| 模型 | AUC | 精确率 | 召回率 |
|---|---|---|---|
| **三等权集成（默认）** | **0.932** | **47.4%** | **73.4%** |
| 随机森林 | 0.909 | 45.5% | 65.2% |
| 直方图梯度提升 | 0.907 | 39.0% | 59.8% |
| 逻辑回归 | 0.900 | 42.7% | 68.5% |
| 支持向量机 RBF | 0.900 | 41.4% | 67.4% |
| 极端随机树 | 0.891 | 41.6% | 57.6% |
| 只用 `pre30`（单特征） | 0.852 | 35.0% | 54.3% |
| **`--model formula`（旧版手工权重）** | **0.563** | **18.5%** | **34.3%** |

> **⚠️ 精确率数字变过三次，必须说明。**
>
> 1. 最初的评估函数是「直接取分数最高的 3 个」，**没有实现工具里的候选
>    抑制、合并和时间吸附** —— 报出去的 60.2% 偏乐观了近 20 个点。
> 2. 我在调参过程中用的临时脚本（`_ml/kde_*`、`_ml/greedy_merge_test.py` 等）
>    还有**第二个 bug**：写的是 `if not gts: continue`，
>    而官方标注里有 **13 轨标着「0 次」**（空列表 `[]`）——
>    这些音轨被**整个跳过**了。它们恰恰是最难的负样本：模型照样输出 3 个候选，
>    全部是误报。跳过它们把精确率虚高了约 **11 个点**（59.3% → 48.1%）。
>    `train_model.py` 用的 `if g is None: continue` 才是对的。
> 3. 还有一个次要差异：`train_model.py` 是**逐折算精确率再取平均**，
>    临时脚本是**全部折汇总后算**。各折候选数不等（12~30 个），
>    两者差约 0.8 个点（48.1% vs 48.9%）。
>
> **AUC 列不受这些影响**（它在全部候选上算，与选哪几个、跳过哪些轨无关），
> 所以「集成 > 随机森林 > 梯度提升 > 逻辑回归 > 单特征」这个排序仍然成立。
>
> **最终口径**：`train_model.py` 直接调用 `climax_finder` 的
> `merge_candidates` + `snap_to_peak`，并保留所有有官方标注的音轨
> （包括「0 次」的空轨）。这是唯一与工具行为一致的口径。

**逐作品 AUC 对比（最能说明问题的一行）：**

| | RJ01525490 | RJ01583845 | RJ01586001 | RJ01589742 | RJ01603181 | RJ01605303 | RJ01610459 | RJ01625306 | RJ324692 | RJ362169 |
|---|---|---|---|---|---|---|---|---|---|---|
| 集成 | 0.973 | 0.918 | 0.881 | 0.977 | 0.950 | 0.973 | 0.953 | 0.909 | 0.903 | 0.878 |
| **旧公式** | 0.537 | 0.616 | **0.460** | 0.711 | 0.597 | **0.310** | **0.468** | 0.628 | 0.753 | 0.549 |

> **旧公式在 RJ01605303 上 AUC 0.310 —— 比随机（0.5）还差，是反相关的。**
> 集成模型的 10 折范围是 0.878 ~ 0.977，**没有任何一折低于 0.85**。
>
> **这不是「精度差一点」，是「有时完全不可用 vs 始终可用」。**

**配对检验（10 折逐折）：** 集成 − 旧公式 AUC **+0.369，10/10 折更好**；精确率 **+41.7 个点，10/10 折更好**。

### 11.2 33 个特征 → 模型用 21 个

| 类别 | 特征 |
|---|---|
| **能量水平**（相对全轨中位数的 dB） | `peak` `pre60` `pre30` `pre10` `post2` `post10` `post30` |
| **构造差值** | `signature` = `pre30 − post2`　`contrast` = `peak − pre10` |
| **形状** | `rise` `decay` `recover` `prominence` `plateau` |
| **轨内上下文** | `rel_time` `rank_energy` `gap_prev` |
| **频谱** | `zcr` `centroid` `flatness` |
| **语义** | `txt`（关键词线索加权分） |

随机森林特征重要性（全部数据拟合，仅供理解）：

```
pre30      0.2054  #####################################################
pre60      0.2008  ####################################################
rel_time   0.1059  ###########################
post30     0.0824  #####################
pre10      0.0570  ##############
centroid   0.0439  ###########
...
signature  0.0269  ######        ← 旧版公式的主力，排第 9
recover    0.0243  ######        ← 排第 10
peak       0.0139  ###           ← 纯能量，几乎没用
txt        0.0129  ###           ← 关键词，几乎没用
```

> **`pre30` / `pre60`（高潮前 30~60 秒的平均能量）是最强的两个特征，合计权重 0.41。**
>
> 直观解释：**真高潮前面通常有一段持续升温的铺垫；而音效爆发前面是安静的。**
> **「爆发之前发生了什么」比「爆发本身长什么样」更有信息量。**

**特征相关性**（21 个特征，3981 个样本）：

```
强相关对（|r| ≥ 0.7）:
  pre10     ↔ contrast     r = -0.873
  centroid  ↔ flatness     r = +0.848
  pre60     ↔ pre30        r = +0.742
  contrast  ↔ prominence   r = +0.735
  pre30     ↔ pre10        r = +0.730

冗余组:
  [5 个] pre60, pre30, pre10, contrast, prominence   ← 都在描述「峰值前的能量水平」
  [2 个] centroid, flatness                          ← 都在描述「频谱形状」
```

`signature` / `contrast` / `pre30` / `post2` 等 6 个特征的 **VIF 是无穷大**——因为它们是其他特征的
**精确线性组合**（`signature` 就是 `pre30 − post2`）。这对线性模型是个真问题
（逻辑回归靠 `C=0.3` 的 L2 正则吸收掉），**对树模型无害**。

**但实测：删冗余特征一律变差。**

| 特征集 | 特征数 | AUC | 精确率 |
|---|---|---|---|
| **全部 21 个** | **21** | **0.919** | **61.1%** |
| 每组只留一个（去冗余） | 16 | 0.878 | 50.4% |
| 只留 5 个 | 5 | 0.876 | 46.5% |
| 只留 1 个（`pre30`） | 1 | 0.832 | 26.7% |

**原因**：树每次分裂只选一个特征，相关特征相当于「多几个备选视角」；
且冗余提供鲁棒性——某特征在某作品失效时，同组另一个还能用。
**随机森林的随机特征子采样本身就是去相关机制。**

> ⚠️ **但特征重要性不能直接读作「有没有用」**：`pre10` 单特征 AUC 0.757（不差），
> 重要性却只有 0.0570——**它的贡献被同组更强的 `pre30` 吸收了。**
> **必须先看相关性再解读重要性，否则会误删被稀释的特征。**

### 11.3 候选合并：30 秒内视为同一次高潮

模型有时把**一次**高潮拆成两个相距 ~20 秒的候选，两者置信度还差不多。
这是用户听着听着发现的，我回头核查了 10 折样本外数据 ——
相距 ≤60 秒的成对候选共 **110 对**：

| 类型 | 对数 | 占比 |
|---|---|---|
| **一次高潮被拆成两个** | **66** | **60%** |
| 其中含误报 | 42 | 38% |
| 真的是两次高潮 | **2** | **1.8%** |

**而且这两类在特征上确实分得开**（"被拆开"组，66 对）：

| 特征 | 前一个点 | 后一个点 | 差 |
|---|---|---|---|
| `post10`（释放后 4~10 秒能量） | **+7.48 dB** | **−0.47 dB** | **−7.95** |
| `post2`（释放后 1.5~4 秒） | +7.82 | +3.36 | −4.46 |
| `recover`（掉到中位数以下用时） | 3.54 s | 1.54 s | −2.00 |

**前一个点有持续约 10 秒的高能量余韵，后一个点立刻塌下去** ——
说明前一个更接近真实爆发点，后一个只是同一次高潮里的次级峰。

> **但不能对整个候选池做合并。** 单链式合并会让簇沿时间轴漂移：
> 实测 20 秒窗口能把 100 多个候选串成一大簇（合并掉 779 个），指标直接崩。
> 所以只考察分数最高的 `top+1` 个，且**只跟簇的代表点比距离**。

参数是实测选的（10 折留一作品，±20 秒容差）：

| 规则 | 精确率 | 召回率 | F1 | 每轨候选 |
|---|---|---|---|---|
| 旧的间隔抑制（15 秒、拉满 3 个） | 41.5% | 68.5% | 0.517 | 2.92 |
| 取前 3 → 合并 30s | 54.3% | 62.0% | 0.579 | 1.48 |
| **取前 4 → 合并 30s（采用）** | **47.0%** | **68.5%** | **0.558** | **1.89** |
| 取前 5 → 合并 30s | 40.8% | 69.6% | 0.514 | 2.21 |
| 取前 8 → 合并 30s | 35.6% | 75.0% | 0.483 | 2.85 |

**取前 4 在每个维度上都优于旧实现**：精确率 +5.5 点、召回率持平、
候选数少 35%、且不再出现「同一次高潮两个条目」。
合并时代表点取**成员时间的中点**（用户观察：真值在两个候选中间）。

时间精度也略有改善：命中候选到最近真值的平均误差 8.5 秒 → 7.9 秒，
误差 ≤10 秒的比例 63% → 70%。

```bat
python climax_finder.py "目录" --merge-gap 30 --pool 4
```

`--merge-gap 0` 可关闭合并（恢复旧行为，用于对照）。

### 11.4 时间吸附：候选池里本来就有准的峰

模型把一次高潮拆成两个候选的问题解决后，还剩一个：**时间不够准**。
实测命中候选到最近真值的平均误差 7.9 秒，只有 35% 落在 5 秒内。

但查下去发现，**候选池里其实一直有很准的峰**：

| 作品 | 模型选中（中位误差） | **离真值最近的峰（中位误差）** |
|---|---|---|
| RJ01583845 | 10.5 秒 | **1.3 秒** |
| RJ362169 | 4.0 秒 | **1.6 秒** |
| RJ324692 | 9.8 秒 | **2.0 秒** |
| RJ01610459 | 9.2 秒 | **2.2 秒** |
| RJ01586001 | 10.8 秒 | **2.4 秒** |

**差距全在「挑哪个峰」上，不在「峰的定义」上。** 也试过换地标
（能量最高点 / 上升最陡 / 起爆点 / 能量重心），**全部更差** ——
能量包络的局部极大值已经是最好的地标。

那为什么模型挑不对？因为它训练的目标是「这附近有没有高潮」，
真值 ±20 秒内的**所有**峰都算正例，**没有动力区分哪个最准**。
试过按距离给样本加权（`w = exp(-(d/σ)²)`）和硬标注（只有最近峰算正例）：
≤5 秒从 35% 提到 43%，但精确率掉 3 个点；硬标注还把 AUC 从 0.916 打到 0.858。
**不划算，没采用。**

近邻峰之间确实有可分的特征（真值 ±15 秒内，「最近峰」对「其它峰」）：

| 特征 | 最近峰 | 其它峰 | 标准化差 |
|---|---|---|---|
| `prominence` | 18.96 | 15.59 | **+0.65** |
| `peak`（绝对能量） | 24.20 | 21.27 | **+0.56** |
| `rank_energy`（轨内排名） | 15.5 | 26.5 | −0.47 |

也就是**最近的那个峰更突出、更响、轨内能量排名更高**。所以选完之后再吸附一次。
窗口扫描（精确率 / 召回率 / ≤5 秒比例 / 平均误差）：

| 吸附窗口 | 精确率 | 召回率 | ≤5 秒 | 平均误差 |
|---|---|---|---|---|
| 不吸附 | 57.8% | 68.5% | 35% | 7.9 秒 |
| ±6 秒 | 57.8% | 68.5% | 43% | 7.6 秒 |
| **±12 秒（采用）** | **57.8%** | **68.5%** | **52%** | **6.8 秒** |
| ±20 秒 | 56.9% | 65.2% | 58% | 6.4 秒 |
| ±25 秒 | 59.6% | 66.3% | 60% | 6.0 秒 |

**±12 秒是「免费」的：精确率和召回率都不变，≤5 秒的比例从 35% 提到 52%。**

选 ±12 而不是 ±25，是因为 **12 秒 < 合并窗口 30 秒** ——
吸附不会跳到相邻的另一次高潮上去。±25 的平均值更好，但 10 部里有 3 部变差。

```bat
python climax_finder.py "目录" --snap 12     :: 默认；--snap 0 关闭
```

#### 后续改进：改用**回归精修**（软标签）

「吸附到能量最大的峰」是启发式的。更好的做法是**训一个专门管时间的模型**，
但它**只做局部精修，不参与全局排序**：

    y = exp(-(d / σ)²)      d = 到最近真值的距离，σ = 2 秒

| 精修方式 | 精确率 | 召回率 | ≤3 秒 | ≤5 秒 | 平均误差 |
|---|---|---|---|---|---|
| 不精修 | 49.1% | 72.5% | 20% | 34% | 8.1 秒 |
| 能量最大精修（旧） | 48.9% | 72.9% | 41% | 53% | 6.5 秒 |
| **回归精修（新）** | **49.7%** | **73.1%** | **46%** | **62%** | **5.5 秒** |

**每一项都不输、多数小胜**：精确率 +0.8、召回率 +0.2、≤5 秒 +9、平均误差 −1.0 秒。

> **为什么不让它参与全局排序？** 试过，会垮：
> 纯用回归分排序 → 精确率 31.2%、召回率 65.9%（虽然 ≤5 秒有 68%）。
> 回归目标（连续、要求精确到几秒）比二分类目标难得多，
> 同样的模型容量拟合不好，整体排序反而变差。
> **分工才是对的：分类器负责「哪里有没有高潮」，回归器负责「具体在哪一秒」。**

窗口越大时间越准、精确率越低：±10 → ≤5 秒 55%；±12（采用）→ 62%；±20 → 66%。

**试过但没采用的方案：核密度估计（KDE）。**
把每个峰看作概率云、按模型分加权、密度叠加后取极大值 ——
形式上是「高潮时刻的最大后验估计」，理论上很漂亮，
而且两个相近的峰叠加后峰值自然落在中间。但实测打不过上面的做法：

| 方案 | 精确率 | 召回率 | 平均误差 | ≤5 秒 |
|---|---|---|---|---|
| **合并 30s + 吸附 12s** | **57.8%** | 68.5% | **6.8 秒** | **52%** |
| 纯 KDE（全部候选，20+ 组参数） | 40.8~46.0% | 65~76% | 7.4~9.5 秒 | 32~45% |
| 混合：取前 8 个再做 KDE | 47.1% | **77.2%** | 7.7 秒 | 46% |

**KDE 的召回率确实高 8.7 点，但精确率掉 10.7 点。**
原因：低分峰扎堆的地方密度虚高，而那往往不是高潮。
对一个「候选生成器」来说精确率才是当前瓶颈（用户要人工筛掉近一半误报），
所以这个交换方向是反的。

### 11.5 集成：为什么是三等权

三个模型的概率取算术平均：

```python
p = (p_随机森林 + p_梯度提升 + p_逻辑回归) / 3
```

**为什么有效：三个模型「错得不一样」。** 实测它们在每部作品上排出的 Top-3，
**10 部里没有任何一次完全一致**，重合度最低只有 30%。

| 作品 | RF∩HGB | RF∩LR | HGB∩LR |
|---|---|---|---|
| RJ01586001 | **33%** | 37% | 30% |
| RJ01583845 | 67% | 40% | 36% |
| RJ362169 | 62% | 45% | **35%** |

**夺冠次数**：集成 5 次、梯度提升 3 次、随机森林 2 次、逻辑回归 0 次。

**方差降低的数学**：三个误差方差同为 σ²、两两相关 ρ 时，
平均后方差 = σ²(1+2ρ)/3。ρ < 1 就有收益。实测 AUC 标准差 0.036，低于任一单模型。

| 集成方案 | AUC | 精确率 |
|---|---|---|
| **三等权 (1/3, 1/3, 1/3)** | **0.931** | **60.2%** |
| 秩平均（转排名后等权） | 0.930 | 59.5% |
| 训练折 AUC 比例加权 | 0.931 | 60.2% |
| 网格搜索权重（内层选） | 0.929 | **59.4%** |
| Stacking（LR 元模型学权重） | 0.930 | 60.1% |

> **所有「更聪明」的加权方案都不比三等权好。**
>
> 原因：三个模型 AUC 只差 0.006（0.923 / 0.917 / 0.917），**数据里本来就没有偏好的依据**。
> 网格搜索每折选出的权重从 (0.2, 0.7, 0.1) 到 (0.4, 0.3, 0.3) 完全不一致——**那是噪声**。
> Stacking 的元模型系数是 RF +3.71 / HGB +0.90 / LR +2.58，
> **差异反映的是三个模型输出尺度不同（梯度提升的概率更饱和），不是在挖掘互补信息。**

### 11.6 置信度：排序用原始分，显示用校准概率

**这两个必须分开，原因见下。**

模型输出的原始分（三等权平均）**不是概率**。实测 10 折样本外：

| 原始分区间 | 候选 | 命中 | **实际命中率** |
|---|---|---|---|
| [0.00, 0.10) | 2297 | 16 | 0.7% |
| [0.10, 0.30) | 1012 | 44 | 4.3% |
| [0.30, 0.50) | 359 | 55 | 15.3% |
| [0.50, 0.70) | 106 | 35 | 33.0% |
| [0.70, 0.85) | 112 | 62 | 55.4% |
| [0.85, 0.95) | 78 | 59 | 75.6% |
| [0.95, 1.00] | 17 | 16 | **94.1%** |

**单调 ✓，是好的排序信号。但原始分本身不能读作概率。**

所以用 **isotonic 回归**（在 10 折样本外预测上拟合）把它映射成真实命中率：

```
Brier 分数：0.0565 → 0.0412（改善 27%）
校准后各区间实际命中率与预测值吻合
```

> **⚠️ isotonic 不能提高精度——它是单调变换，不改变任何两个候选的相对顺序。**
>
> 有些评测会看到「精确率 +0.9 个点」，**那是噪声**：10 折里只有 2 折上升、1 折下降、7 折不变，
> 全靠 RJ01605303 一折（18 个输出）多命中 2 个。而且 isotonic 会把分数压成阶梯
> （实测 252 个候选压成 21 个取值，最大一组 100 个并列），**用它排序反而略降 AUC（−0.0018）**。
>
> **所以本工具的设计是：**
> ```
> 排序 → 原始分（保持 AUC 0.931）
> 显示 → isotonic 校准概率（让「62%」真的意味着 62%）
> ```
> **校准不改变精度，只改变「你能否相信那个数字」。**

概率封顶 95%：样本外最高区间的实测命中率是 94.1%（仅 17 个样本），
isotonic 会在极少数全正样本块上映射到 100%，那是在给用户「绝对确定」的错觉。

### 11.7 ⚠️ 早期版本的两个错误论断（已被实验推翻）

工具早期版本（`--model formula`）基于 2 部作品 / 21 个标注点，写下了现在看是错的结论：

**错误 1：「高潮 = 持续高涨的平台 → 爆发 → 迅速脱力下坠」**

那个结论是用**全部局部极大值**当负样本测出来的——而其中绝大多数是**安静时刻**。
**工具真正要面对的对手是「同样响亮的其它时刻」。** 换个口径，方向就反了：

| 特征 | vs 池内响亮负样本 | vs 池外安静时刻 |
|---|---|---|
| `signature` | 0.614 | 0.623 |
| `recover` | **0.511**（几乎随机） | 0.234 |
| `pre30` | **0.818** | 0.852 |
| `post4` | **0.401**（方向相反） | 0.369 |
| **`peak`（纯能量）** | **0.558**（几乎随机） | **0.954**（几乎完美） |

**看 `peak` 那一行**：跟安静时刻比，能量几乎完美（0.954）；跟其它响亮时刻比，能量毫无用处（0.558）。
**「能量 AUC 0.566」和「能量 AUC 0.954」都对——取决于跟谁比。**

**错误 2：`signature` 和 `recover` 是最强特征**

它们是在错误口径下选出来的。**在学习真正要解决的问题时，它们的重要性排第 9 和第 10**，
而 `pre30`/`pre60` 才是主力（合计 0.41）。

**教训：负样本的选取决定了你能看到什么。**
用「容易的负样本」做特征选择，会选出「擅长区分容易样本」的特征。

### 11.9 为什么精确率只有一半：要跟上限比

**先看官方标注里每轨有几个高潮点**：

| 每轨高潮数 | 轨数 | 占比 |
|---|---|---|
| 0 | 13 | 18% |
| **1** | **37** | **52%** |
| 2 | 12 | 17% |
| 3 及以上 | 9 | 13% |

**过半的音轨只有 1 个高潮，而工具每轨最多输出 3 个候选** ——
结构上就有 2 个位置注定是错的。这是精确率上不去的主要原因，不是模型不行。

**训练报告里的 47.9% / 73.5% 是「不过滤」的数字** —— 所有合并后的事件都算。
但界面和命令行默认有门槛，低分候选根本不显示。**两个口径都要看**：

| | 精确率 | 召回率 | F1 | 每轨候选 |
|---|---|---|---|---|
| 不过滤（	rain_model.py 上面那份报告） | 49.7% | 74.3% | 0.595 | 1.87 |
| **≥50%（界面/命令行默认）** | **72.7%** | **69.0%** | **0.708** | 1.17 |

**门槛扫描**（同一模型、同一选取方式，只改输出门槛）。
门槛比的是**校准概率**，与界面显示的一致：

| 最低概率 | 逐折精确率 | 逐折召回率 | F1 | 每轨候选 | ≤5 秒 |
|---|---|---|---|---|---|
| 不过滤 | 49.7% | 73.1% | 0.592 | 1.87 | 62% |
| ≥17% | 59.3% | 73.1% | 0.655 | 1.56 | 62% |
| ≥25% | 69.0% | 68.9% | 0.689 | 1.25 | 63% |
| **≥50%（WebUI 默认）** | **72.7%** | **67.8%** | **0.701** | 1.17 | 64% |
| ≥66% | 87.1% | 56.6% | 0.686 | 0.80 | 67% |
| ≥67% | **98.0%** | 41.4% | 0.582 | 0.51 | 63% |

> ≥67% 时精确率 **98.0%** —— 模型一旦非常自信，几乎不会错。

> ⚠️ 这张表修正过两次。
> 1. 最初那版用的是**原始分**，而界面比的是**校准概率**，
>    两者尺度差很远（原始分 0.7 ≈ 校准概率 0.51），数字对不上界面行为。
> 2. 选项只列 **isotonic 校准真实产生的台阶**。校准把连续分压成了 19 个取值，
>    在台阶之间设门槛**完全无效** —— 实测 ≥52% / ≥55% / ≥58% / ≥60% 结果一模一样。
>    所以列了也没用。

**一个真实的例子**（RJ01586001 第 1 轨，官方标注是 **0 次高潮**）：

| 门槛 | 输出 |
|---|---|
| 不过滤 | 5 个候选，全是噪声（7% / 3% / 2% / 0% / 0%） |
| ≥17% | **0 个 —— 正确地弃权** |

工具会说「我没找到值得给你看的」，而不是硬塞噪声凑数。

**「50% 是不是最优？」——是。** 穷举全部 133 个候选前缀（任意门槛能达到的所有点）：

| 口径 | 精确率 | 召回率 | F1 |
|---|---|---|---|
| **校准概率 ≥50%（当前默认）** | 70.5% | 67.5% | **0.690** |
| 原始分连续门槛最优（≥0.62） | 69.9% | 68.6% | **0.693** |
| 穷举全部前缀的全局最优 | 69.9% | 68.6% | **0.693** |

**当前默认距离理论全局最优只差 0.003。** 台阶粗，但没有代价 ——
因为分数分布本身就把「高精度候选」和「噪声」分得够开。

**模型在自信的时候非常准 —— ≥70% 时精确率 91.8%。**
48.9% 是「每轨硬输出 3 个」逼出来的，不是模型分辨不出。

**WebUI 的「最低概率」默认 50%（准 71% / 全 66%），并且把每个档位的实测
精确率/召回率直接写在选项上** —— 质量取舍自己权衡，工具不替你决定。

> **设计原则：--top 是上限，不是目标。** 候选少就少给，
> 绝不为了凑够 3 个而塞低分候选。merge_candidates 只返回
> 「确实超过门槛的不同事件」，一轨只给 1 个也是正常的。

### 11.10 训练集内 vs 留一作品（过拟合有多大）

| | 逐折精确率 | 逐折召回率 | 平均时间误差 |
|---|---|---|---|
| 训练集内（10 部全用来训） | 63.7% | 82.9% | 4.9 秒 |
| 留一作品（9 部训 1 部测） | 48.9% | 72.9% | 6.5 秒 |
| **过拟合幅度** | **+14.8** | **+10.0** | **−1.6 秒** |

**确实有明显过拟合（+14.8 个点）。** 但要注意两点：

1. **训练集内也只有 63.7%** —— 这不是「记住了就满分」。
   随机森林 min_samples_leaf=5, max_depth=10 本来就不是能背下 3981 行的容量，
   而且标签本身是模糊的（真值 ±20 秒内的峰**全算正例**，几十个峰同标为正）。
2. **你在播放器里分析的那两部（RJ01211672 / RJ01575513）不在训练集里**，
   所以感受到的是 ~49% 的留出性能，而不是 63.7%。
   等你标完、把它们训进模型，这两部才会享受「训练集内」的表现。

### 11.11 ASR 到底贡献了多少

	xt 是 21 个特征里唯一来自 ASR 转写的。把它整个去掉重测：

| 特征集 | 逐折精确率 | 逐折召回率 | 汇总精确率 | 汇总召回率 |
|---|---|---|---|---|
| 全部 21 个（含 	xt） | 48.9% | 72.9% | 48.1% | 68.5% |
| 20 个（去掉 	xt） | 47.2% | 71.2% | 47.0% | 67.4% |
| **差异** | **−1.7** | **−1.7** | **−1.1** | **−1.1** |

**ASR 贡献约 1.7 个点。** 不是零，但很小。

要点：**推理时完全不需要 ASR**。它只在准备训练数据时跑过一次（8~19× 实时），
而且这个项目本来就要跑 ASR 做 LRC 翻译，所以没有额外成本。
播放器读转写文件是「顺便用上」，没有转写也能跑（--acoustic-only）。

### 11.12 局限（必须知道）

1. **精确率 60%** —— 约 4 成的候选是错的，**必须人工确认**
2. **召回率 70%** —— 有 3 成的高潮点排不进每轨前 3
3. **只有 10 部作品 / 92 个标注点**，置信区间仍然宽
4. **标注本身有误差** —— 多部 readme 写着「高潮时间只是大概」，所以容差取 ±20 秒
5. **校准概率是封顶 95% 的**，不是 100%；且高概率区间的样本很少（≥0.95 只有 17 个）
6. **短于 60 秒的音轨直接跳过** —— 实测 5 秒的标题轨能拿到极高分数，短轨特征不稳定
7. **`--model formula` 已不推荐使用** —— 10 折实测精确率仅 18.5%，且在某部作品上 AUC 0.310
8. **语义特征重要性只有 0.013** —— 关键词规则实测帮助很小；
   真正有用的是「能量演进」这种**语境**信息，而关键词匹配抓不到语境

### 11.13 换作品时的建议流程

1. **先跑一遍看最高校准概率** —— 若整轨都低于 30%，工具会提示「可能没有高潮」
2. **对照实际音频听几个候选**，确认精度是否可接受
3. **用 `--min-score 0.5` 只输出高置信候选**（精确率显著上升，召回率下降）
4. **如果某部作品明显更差** —— 检查它是不是音效特别密集（`--acoustic-only` 对比看看）
5. **不要为了单部作品去调模型权重** —— 实测调权重只会拟合噪声
